# Backend v0.8: Barcode, Import and System Integration

## Goal
Support the remaining three ways to update stock:
1. **Barcode scanning**: look up a product by barcode, then record a movement with `source = BARCODE`.
2. **CSV / Excel import**: upload a file, validate every row (dry run), then commit everything or nothing.
3. **System integration**: other systems post movements using an API key instead of a user login.

## Prerequisites
Backend v0.7 is done.

## Part A: Barcode

1. `GET /api/products/barcode/{code}` returns the `ProductResponse`, or 404. Any logged-in user can call it.
2. The receipt and issue requests already accept `source`. Validate that clients can only send `MANUAL` or `BARCODE`. `IMPORT`, `INTEGRATION` and `SYSTEM` are set by the server only.

That's all the barcode support the backend needs. Scanning itself happens in the browser.

## Part B: CSV / Excel import

### Dependencies
```groovy
implementation 'org.apache.commons:commons-csv:1.14.1'
implementation 'org.apache.poi:poi-ooxml:5.4.1'
```
(Check Maven Central for the latest versions.)

`application.yml`:
```yaml
spring:
  servlet:
    multipart:
      max-file-size: 5MB
      max-request-size: 5MB
```

### File format
Columns, with a header row: `sku_or_barcode,type,quantity,reference,reason`

| type | quantity means | reason |
|---|---|---|
| `RECEIPT` | units in (> 0) | optional |
| `ISSUE` | units out (> 0) | optional |
| `ADJUSTMENT` | counted quantity (>= 0) | required |

Transfers can't be imported, because they need two branches.

### `ImportFileParser`
- `List<ImportRow> parse(MultipartFile file)` picks a parser by file extension: `.csv` uses Commons CSV (`CSVFormat.DEFAULT.builder().setHeader().setSkipHeaderRecord(true).get()`), and `.xlsx` uses POI (`new XSSFWorkbook(in)` and reads the first sheet). Any other extension returns 400.
- `ImportRow(int rowNumber, String skuOrBarcode, String type, String quantity, String reference, String reason)`. Keep everything as **raw strings**: converting them is the validator's job, and it lets you report bad values per row.
- Use `DataFormatter` for Excel cells, so numbers and text both come back as strings.
- Limit the file to 1000 rows (400 if over).

### `ImportService`
```text
ImportReport importMovements(MultipartFile file, Long branchId, boolean dryRun)
byte[] template(String format)
```
How `importMovements` works:
1. `guard.check(branchId)`, then parse the file.
2. Validate every row and collect an `ImportRowResult(rowNumber, status OK|ERROR, message)` for each:
   - The product is found by SKU **or** barcode and is active.
   - The type is one of the three allowed, and the quantity is an integer within its rule.
   - **Projected balance**: keep a `Map<productId, Integer>` starting from the current stock levels, apply each row in order, and flag any row that would make the balance negative. This catches "issue 10, then issue 10" when only 15 are in stock. It's the most interesting logic in this version.
3. If there are any errors, **or** `dryRun` is true, return the report and save nothing.
4. Otherwise build `MovementCommand`s (`source = IMPORT`, reference defaults to the file name) and call `stockMovementService.applyBatch(...)`, which runs as one transaction. Record one `IMPORT` audit entry with the file name and row count.

`ImportReport(String fileName, int totalRows, int okRows, int errorRows, boolean committed, List<ImportRowResult> rows)`

### `ImportController`
| HTTP | Path | Notes |
|---|---|---|
| POST | `/api/imports/movements` | `multipart/form-data` with parts `file`, `branchId`, `dryRun` (default `true`). `hasAnyRole('ADMIN','MANAGER')` |

## Part C: System integration (API key)

### `ApiClient` entity and seed
- `ApiClient`: `name`, `keyHash` (unique), `branch` (ManyToOne), `active`.
- Hash keys with **SHA-256**, stored as hex. You can't use BCrypt here: the filter has to *look up* the client by its hash, and BCrypt adds a random salt, so the same key would give a different hash each time. API keys are long random strings, so a fast hash is acceptable for them, unlike passwords.
- `seed/api-clients.json`: `[{ "name": "POS KL01", "key": "dev-pos-kl01-0b7c9e2f4a", "branch": "KL01" }]`. The seeder hashes the key.

### `ApiKeyAuthFilter extends OncePerRequestFilter`
- It reads the `X-API-Key` header. If it's missing, the filter leaves the request alone, so it ends up as 401.
- Hash the key, then look up an active client. If one is found, put a `UsernamePasswordAuthenticationToken` in the security context with principal `"api:" + name` and authority `ROLE_INTEGRATION`. Store the branch id in the token's `details`.

### Second filter chain in `SecurityConfig`
```java
@Bean @Order(1)
SecurityFilterChain integrationChain(HttpSecurity http) { /* securityMatcher("/api/integration/**"), stateless,
   csrf off, addFilterBefore(apiKeyFilter, AuthorizationFilter.class), anyRequest().hasRole("INTEGRATION") */ }
```
Your existing JWT chain becomes `@Order(2)`. Update `CurrentUser` so it understands both kinds of principal (a `Jwt` and the API-client token).

Don't annotate `ApiKeyAuthFilter` with `@Component`. Spring Boot automatically registers servlet filters that are beans, so it would also run on every other request. Create it with `new` inside the chain bean instead.

### Integration endpoint
`POST /api/integration/movements`:
```json
{ "items": [ { "sku": "SKU-001", "type": "ISSUE", "quantity": 2, "reference": "POS-778812" },
             { "barcode": "9555000000080", "type": "RECEIPT", "quantity": 10, "reference": "GRN-5521" } ] }
```
The branch always comes from the API client, never from the request body. `IntegrationService` resolves the products and calls `applyBatch` with `source = INTEGRATION` (all or nothing). It returns `201 List<MovementResponse>`, and 409 if any item is short.

## Done checklist
- [ ] `GET /api/products/barcode/9555000000011` returns A4 Paper; an unknown code returns 404
- [ ] A receipt with `"source": "IMPORT"` from the normal API returns 400
- [ ] The template downloads as both CSV and XLSX and opens in Excel
- [ ] A dry run of a file with one bad SKU and one over-issue reports exactly those two rows and saves nothing
- [ ] Committing a valid file creates movements with `source = IMPORT` and one `IMPORT` audit entry
- [ ] Committing a file that has errors returns the report with `committed: false`
- [ ] `POST /api/integration/movements` with no key or a wrong key returns 401; with the dev key it creates movements at KL01
- [ ] A JWT does **not** work on `/api/integration/**`, and the API key doesn't work on `/api/products`
