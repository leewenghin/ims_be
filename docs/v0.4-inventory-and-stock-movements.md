# Backend v0.4: Inventory and Stock Movements

## Goal
Build the heart of the system: per-branch stock levels driven by an append-only movement ledger. Receipts, issues, adjustments and transfers are all atomic and safe under concurrent requests.

## Prerequisites
Backend v0.3 is done.

## Concepts first
- **Ledger**: `stock_movement` rows are facts ("5 units left KL01 at 10:02"). You never update or delete them. Mistakes are fixed with a new `ADJUSTMENT`.
- **Running balance**: `stock_level.quantity` exists so reads are fast. It must always equal the sum of the deltas.
- **Atomicity**: the movement insert and the stock level update happen in one `@Transactional` method. If either fails, both roll back.
- **Optimistic locking**: `@Version` on `StockLevel`. If two requests read version 3 and both try to write, the second gets `ObjectOptimisticLockingFailureException` instead of silently overwriting the first.

## Steps

### 1. Enums
- `MovementType { RECEIPT, ISSUE, ADJUSTMENT, TRANSFER_OUT, TRANSFER_IN }`
- `MovementSource { MANUAL, BARCODE, IMPORT, INTEGRATION, SYSTEM }`. `SYSTEM` is used by the seeder.

Store enums with `@Enumerated(EnumType.STRING)`. Never use `ORDINAL`: reordering the enum would corrupt existing data.

### 2. `StockLevel` entity
| Field | Mapping |
|---|---|
| branch | `@ManyToOne(fetch = LAZY, optional = false)` `@JoinColumn(name = "branch_id")` |
| product | `@ManyToOne(fetch = LAZY, optional = false)` `@JoinColumn(name = "product_id")` |
| quantity | `int`, not null |
| version | `@Version Long` |

```java
@Table(name = "stock_level",
       uniqueConstraints = @UniqueConstraint(name = "uk_stock_branch_product", columnNames = {"branch_id", "product_id"}),
       check = @CheckConstraint(name = "ck_stock_qty_non_negative", constraint = "quantity >= 0"))
```
(`@CheckConstraint` is new in Jakarta Persistence 3.2, which Boot 4 uses.)

Add a domain method `void apply(int delta)` that throws `InsufficientStockException` if `quantity + delta < 0`. Keeping the rule inside the entity means it can't be bypassed.

It doesn't need `BaseEntity` timestamps, but extending it is fine.

### 3. `StockMovement` entity
Fields: `type`, `source`, `branch` (ManyToOne), `product` (ManyToOne), `int quantityDelta` (signed), `int balanceAfter`, `String reference` (length 100), `String reason` (length 255), `UUID transferId` (nullable), `String createdBy` (username, `"system"` until v0.5), `Instant createdAt`.

Indexes: `(branch_id, created_at)`, `(product_id)`, `(transfer_id)`.

Make it effectively immutable: a constructor with all fields, getters only, no setters.

### 4. Repositories
- `StockLevelRepository`:
  - `Optional<StockLevel> findByBranchIdAndProductId(Long branchId, Long productId)`
  - `boolean existsByBranchIdAndQuantityGreaterThan(Long branchId, int qty)`, used to block branch deactivation (go back to the TODO from v0.3)
  - A JPQL list for inventory that fetches product and branch in one go:
    ```
    select s from StockLevel s join fetch s.product p join fetch s.branch b
    where b.id = :branchId and (:lowOnly = false or s.quantity <= p.reorderLevel)
    order by p.name
    ```
- `StockMovementRepository extends JpaRepository<StockMovement, Long>, JpaSpecificationExecutor<StockMovement>`, so filtering uses Specifications.

### 5. Request DTOs (all validated)
- `ReceiptRequest(@NotNull branchId, @NotNull productId, @Positive quantity, reference, source)`. `source` defaults to `MANUAL`. Only `MANUAL` or `BARCODE` are allowed from the API.
- `IssueRequest`: same fields as `ReceiptRequest`.
- `AdjustmentRequest(@NotNull branchId, @NotNull productId, @PositiveOrZero countedQuantity, @NotBlank reason)`. This is a stock count: the service computes `delta = counted - current`. If delta is 0, reject it with 400 ("nothing to adjust").
- `TransferRequest(@NotNull fromBranchId, @NotNull toBranchId, reference, @NotEmpty @Valid List<TransferItem> items)` with `TransferItem(@NotNull productId, @Positive quantity)`. Rules: from must not equal to, and no duplicate products.
- `MovementCommand(branchId, productId, MovementType type, int quantity, MovementSource source, String reference, String reason)` is the internal shape that import, integration and the seeder use.

### 6. `StockMovementService` (most important class)
```text
MovementResponse receive(ReceiptRequest r)
MovementResponse issue(IssueRequest r)
MovementResponse adjust(AdjustmentRequest r)
TransferResponse transfer(TransferRequest r)
List<MovementResponse> applyBatch(List<MovementCommand> commands)
PageResponse<MovementResponse> search(MovementFilter f, Pageable p)

private StockMovement record(Branch b, Product p, MovementType type, int delta,
                             MovementSource source, String reference, String reason, UUID transferId)
```
What `record` does:
1. Load the `StockLevel` for (branch, product), or create a new one with quantity 0 if it doesn't exist yet.
2. `level.apply(delta)`. This throws if stock would go negative.
3. Save the level, then save a new `StockMovement` with `balanceAfter = level.getQuantity()`.
4. Return the movement.

Rules:
- Each public method is `@Transactional`.
- Branch and product must exist **and be active** (throw 404 or 409 otherwise).
- `transfer` generates one `UUID transferId`. For each item it records `TRANSFER_OUT` (-qty) at the source branch and `TRANSFER_IN` (+qty) at the destination. If any item fails, the whole transfer rolls back.
- `applyBatch` runs all commands in one transaction (all or nothing).
- `search` builds a `Specification` from the optional filters `branchId`, `productId`, `type`, `from`, `to`. Sort by `createdAt desc`.

## API contract
`POST /api/movements/issues`
```json
{ "branchId": 2, "productId": 2, "quantity": 10, "reference": "SO-1001" }
```
`409` (KL01 has only 8)
```json
{ "title": "Insufficient stock", "status": 409, "detail": "SKU-002 at KL01: available 8, requested 10",
  "available": 8, "requested": 10 }
```
`POST /api/movements/transfers`
```json
{ "fromBranchId": 1, "toBranchId": 2, "reference": "TR-0001",
  "items": [ { "productId": 1, "quantity": 50 }, { "productId": 4, "quantity": 20 } ] }
```
`201`
```json
{ "transferId": "4f1c...", "movements": [ { "type": "TRANSFER_OUT", "branchCode": "HQ", "sku": "SKU-001", "quantityDelta": -50, "balanceAfter": 150 }, "..." ] }
```

## Done checklist
- [ ] Opening stock appears in `GET /api/inventory?branchId=...`, and `lowOnly=true` shows only the low items
- [ ] A receipt increases the stock level and appears in `GET /api/movements`
- [ ] Issuing more than is available returns 409, and **no** movement row is created
- [ ] An adjustment to `countedQuantity` sets the level exactly and records the signed delta
- [ ] A transfer creates 2 rows per item sharing one `transferId`. A transfer where one item is short changes nothing at all.
- [ ] In the H2 console, `select branch_id, product_id, sum(quantity_delta) from stock_movement group by 1,2` matches `stock_level`
- [ ] Deactivating a branch that still has stock returns 409

## Stretch
- Try a pessimistic lock instead (`@Lock(LockModeType.PESSIMISTIC_WRITE)` on the level lookup) and compare the two approaches.
- Add automatic retry for optimistic lock failures (one retry, with a fresh transaction).
- Add `GET /api/inventory/summary` with totals per branch.
