# Backend v0.7: Audit Log

## Goal
Record who did what, when, and to which record, for every write and every login attempt. Audit entries can never be edited through the API.

## Prerequisites
Backend v0.6 is done.

## Files

| Layer | Path |
|---|---|
| entity | `entity/AuditLog.java`, `entity/AuditAction.java` |
| repository | `repository/AuditLogRepository.java` |
| dto | `dto/AuditLogResponse.java`, `dto/AuditFilter.java` |
| service | `service/AuditService.java` |
| controller | `controller/AuditController.java` |

## Steps

### 1. Model
- `enum AuditAction { LOGIN_SUCCESS, LOGIN_FAILED, CREATE, UPDATE, DEACTIVATE, PASSWORD_CHANGE, STOCK_MOVEMENT, IMPORT }`
- `AuditLog`: `actor` (username String), `action` (`@Enumerated(STRING)`), `entityType` (String: `PRODUCT`, `BRANCH`, `USER`, `STOCK_MOVEMENT`, `IMPORT`), `entityId` (Long, nullable), `branchId` (Long, nullable), `details` (`@Lob` or `length = 4000`, holds JSON text), `createdAt`.
- Indexes: `(created_at)`, `(entity_type, entity_id)`, `(actor)`.
- Immutable: no setters, and no update or delete methods anywhere.

### 2. `AuditService`
```text
void record(AuditAction action, String entityType, Long entityId, Long branchId, Object details)
void recordLoginFailure(String username)
PageResponse<AuditLogResponse> search(AuditFilter f, Pageable p)
```
- `record` gets the actor from `CurrentUser` and serializes `details` with the injected `JsonMapper`, for example `Map.of("before", oldDto, "after", newDto)`.
- `record` uses the default propagation (`REQUIRED`), so it **joins the caller's transaction**. If the business change rolls back, its audit entry rolls back too. That's what you want.
- `recordLoginFailure` is the exception. The login fails (an exception is thrown), but the audit row must still be saved. Annotate it with `@Transactional(propagation = Propagation.REQUIRES_NEW)` so it commits in its own transaction. This is the classic example of when `REQUIRES_NEW` is the right choice.
- `search` uses a Specification over `actor`, `action`, `entityType`, `entityId`, `branchId`, `from`, `to`, sorted by `createdAt desc`.

### 3. Hook into every write
| Where | Call |
|---|---|
| `AuthService.login` success | `record(LOGIN_SUCCESS, "USER", user.id, user.branchId, null)` |
| `AuthService.login` failure | `recordLoginFailure(username)`, then rethrow |
| `ProductService` create/update/deactivate | `CREATE` / `UPDATE` (with before/after) / `DEACTIVATE` |
| `BranchService` create/update/deactivate | same |
| `UserService` create/update/deactivate/password | same. **Never put passwords in `details`**. |
| `StockMovementService.record` | `STOCK_MOVEMENT` with type, delta, balanceAfter, reference |

To capture "before", build the response DTO **before** you modify the entity.

### 4. `AuditController`
`GET /api/audit` with filter params and paging. Use `@PreAuthorize("hasAnyRole('ADMIN','MANAGER')")`, and in the service, `branchId = guard.resolve(branchId)`.

`AuditLogResponse(id, actor, action, entityType, entityId, branchId, JsonNode details, createdAt)`. Parse the stored text back into a `JsonNode` so the client gets real JSON, not an escaped string.

There are no POST, PUT or DELETE endpoints.

## Done checklist
- [ ] A product update produces an `UPDATE` entry whose `details.before.name` and `details.after.name` differ
- [ ] A failed login creates `LOGIN_FAILED` even though the login request returns 401
- [ ] A rejected issue (409, insufficient stock) creates **no** audit row, because it rolled back with the business change
- [ ] A transfer creates one audit row per movement
- [ ] `manager` only sees KL01 entries; `staff` gets 403
- [ ] No audit `details` contains a password or hash

## Stretch
- Use a Spring `ApplicationEvent` with `@TransactionalEventListener(phase = AFTER_COMMIT)` instead of direct calls, and compare the trade-offs: decoupling vs. losing the shared transaction.
- Look into Hibernate Envers for automatic entity history.
